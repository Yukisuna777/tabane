Tabane — 音声オーケストレーション

声で指揮役の claude に依頼すると、tabane のペインが増えて子セッションが立ち上がり、勝手に作業して、終わったことが指揮役に返ってくる。実装するのは「ペインを外から操作する口」だけで、耳と指揮は既存のものを組み合わせる。

ステータス：ドラフト（承認待ち） 規模：中 前提：tabane v0.1.1 2026-07-28

1. 目的

Claude Code の音声入力（/voice）はセッション内でしか使えない。既に開いているセッションに向かって喋ることはできるが、そこから新しい作業を起こす手段がない。また、走行中のセッションに外から入力を差し込む公式な口も存在しない。

tabane は PTY を直接握っているため、この2つの空白をどちらも埋められる。「ペインを開いて claude を起動しプロンプトを渡す」口を外部に開ければ、声を受けた指揮役の claude が子セッションを生やせるようになる。

実装が必要なのは口だけ。耳は /voice（実装ゼロ）、指揮役は普通の claude ペイン（実装ゼロ）で足りる。あわせて、この口を持つことで返事待ち検知の根拠を「出力の推測」から「エージェント本人の申告」に引き上げられる。これは音声と無関係に tabane 本体の精度向上になる。

2. スコープ

やること
  • tabane CLI（open / list / wait / kill / report）
  • main プロセスに Unix domain socket サーバ（双方向）
  • main → renderer のペイン生成イベント（shared/types.ts に IPC 契約を追加）
  • 子起動時の hooks 注入（--settings で子にだけ渡す）
  • エージェント状態（running / done / needs_input）をペイン状態とは別に保持
  • 権限モード指定（strict / edit / yolo、既定 strict）
  • 同時ペイン数の上限と、全ペイン緊急停止
  • CLI をパスに通すメニュー項目（VS Code の code コマンド方式）
やらないこと
  • 読み上げ（TTS）。Claude Code に機能がなく、マイクが拾う echo 問題も出る
  • LLM に走行中の TUI をキー操作させる。再描画・タイミング・権限プロンプトで事故る
  • 音声での権限承認（誤爆の代償が大きい）
  • 音声認識の自前実装。/voice を使う（動かないと判明した場合のみ再検討）
  • MCP サーバ化。socket プロトコルを共通土台にしておき、必要になってから薄く被せる
  • リモート / SSH 対応。/voice がリモート非対応と明言されている
  • 指揮役 claude の常駐・自動起動。ペインを人間が立てて役割を与えるだけ
why: 3層（耳 / ペイン操作 / 指揮）のうち、耳と指揮は既存機能の組み合わせで手に入る。実装が必要なのは中央の1層だけという分解が本仕様の骨子。「音声専用セッション」のような特別なモードは作らない（コードが増えて得るものがない）。

3. 処理フロー

指揮役ペインで /voice→ 声で依頼→ 指揮役が tabane open→ socket → main→ renderer がペイン追加→ 子 claude 起動（hooks 付き）→ 作業→ Stop hook → tabane report→ 状態確定→ tabane wait が返る→ 指揮役が結果を報告
why: 指揮役はターン制なので、子の完了に自分で気づけない。ポーリングだと人間が毎回尋ねる必要があり、PTY への割り込み通知だと人間の入力中にも刺さって暴走の停止が難しくなる。指揮役が自分のターンの中でブロックして待つwait なら、割り込みを起こさずに「3つ投げて全部終わるまで待つ」が自然に書ける。

指揮役ペインの置き場所

指揮役は ~/develop（アンブレラフォルダ）で起動する。子ペインの cwd はそれぞれ独立しているため、1枚の指揮役に対して別プロジェクトの子を並べるのが主な使い方になる。

ID  TITLE      CWD
1   指揮        ~/develop            ← ここに喋る
2   記事修正    ~/develop/yuki-home
3   ツール改修  ~/develop/yuki-tools
4   配信まわり  ~/develop/SparkCast
why: 理由は2つ。①「yuki-home の記事を直して」から --cwd を導くには、指揮役がプロジェクトの所在を知っている必要がある。~/develop/CLAUDE.md にリポジトリ一覧の表が既にあるため、そこで起動すればプロジェクト辞書として機能し、tabane 側に一覧取得コマンドを作らずに済む。②特定リポジトリ内で起動すると、そのリポの CLAUDE.md を読み込んで文脈を背負ってしまう。指揮役は横断役なのでどのリポにも属さない方がよい。これは ~/develop/CLAUDE.md の「横断作業はアンブレラで起動する」という既存ルールとも一致する。

4. アプローチ案

4-1. ペインを操作する口の形

案内容トレードオフ採否
ACLI + Unix domain socket（双方向）結果を返せるので list / wait が成立する。権限は Bash(tabane:*) の allowlist 一発。人間もシェルから同じコマンドを使えるのでデバッグしやすい採用
BElectron の second-instance（アプリを引数付きで起動し既存インスタンスにイベントを飛ばす）実装は最小だが一方向で結果を返せず、list / wait が作れない。毎回 Electron 起動で 0.3〜1 秒かかる—
CMCP サーバとして tabane を公開型付きツールとして見えるのが利点。ただし実体は同じ socket に行き着くため、CLI の上に後から被せられる。今作る必然がない将来拡張
Dファイル / ディレクトリ監視によるコマンドキュー結果が返せない、レース、ゴミ掃除、watcher が必要。socket より楽な点がない—

4-2. エージェント状態の作り方

案内容トレードオフ採否
Ahooks で子に申告させ、ペイン状態と別軸で保持推測でなく事実。「完了」と「暇」を区別できる。人間が見る glow も同時に正確になる。素のシェルや hooks を持たない CLI は従来の BEL 検知のまま動く採用
B既存の idle / busy / waiting をそのまま CLI で見せる実装は最小。ただし長考中の claude が idle に落ち、完了と暇が区別できない。指揮役が誤った状態を読んで次を投げる事故が起きる—
CBEL / OSC の推測をやめ、hooks の申告だけを根拠にする状態は最も正確になるが、claude 以外を動かしているペインが一切光らなくなる。tabane が「claude 専用端末」に狭まる—
注意: hooks はユーザーのリポジトリの .claude/settings.json を書き換えない。子プロセスにだけ --settings で渡す。プロジェクト設定を汚すと tabane 外の作業にも漏れる。

4-3. 子の完了を指揮役に伝える方法

案内容トレードオフ採否
Aブロッキング tabane wait指揮役が自分のターン内で待つため割り込みが起きない。複数ペインの待ち合わせが自然に書ける。Bash の実行時間上限があるためタイムアウト指定が必須採用
Bポーリング（人間が尋ねたときだけ list）実装最小で予期しない動きをしない。ただし「終わったら次をやっておいて」が成立しない補助として併存（list は実装する）
CPTY プッシュ（tabane が指揮役ペインに書き込んで Enter）最も Live らしいが、人間の入力中にも刺さる。連鎖して勝手に増殖したとき止めにくい—

5. コマンド仕様

tabane open

ペインを1枚追加し、指定 cwd で claude を起動してプロンプトを渡す。プロンプトは起動引数として渡す（起動後の TUI へ流し込むのはタイミング依存で脆いため）。

$ tabane open --cwd ~/develop/yuki-home \
             --prompt "記事の下書きを直して" \
             --title "記事修正" \
             --permission edit
pane 3
  • --cwd … 必須。存在しなければエラー
  • --prompt … 省略時は claude を起動せずシェルだけ開く
  • --title … ペインのタイトルバーに出す名札。省略時は cwd のベース名
  • --permission … strict（既定） / edit / yolo
  • 同時ペイン数が上限に達している場合はエラーを返し、ペインを作らない

tabane list

全ペインの状態を返す。--json で機械可読。

$ tabane list
ID  TITLE      CWD                     AGENT        PANE
1   指揮        ~/develop               -            idle
2   記事修正    ~/develop/yuki-home     done         idle
3   ツール改修  ~/develop/yuki-tools    running      busy
4   配信まわり  ~/develop/SparkCast     needs_input  waiting
  • AGENT … hooks で申告されたエージェント状態。claude 以外を動かしているペインは -
  • PANE … 従来どおり PTY 出力から推測するペイン状態。人間が見る glow の根拠
  • 子ペインの cwd はそれぞれ独立。1枚の指揮役に対して、別プロジェクトの子を並べるのが主用途

tabane wait

指定ペインが done または needs_input になるまでブロックする。複数指定すると全部が決着するまで待つ。

$ tabane wait 2 3 4 --timeout 600
pane 2 done
pane 4 needs_input
pane 3 done
  • --timeout … 秒。既定値は残論点。切れた場合はエラーではなく現在の状態を返して正常終了する（「まだ走っている」も情報のため）
  • 対象ペインが途中で閉じられた場合は closed として返す

tabane kill

ペインを閉じる。--all で全ペインを停止（緊急停止）。

注意: 緊急停止は指揮役 LLM を経由しない経路も必ず持つ（アプリのメニュー / ホットキー）。指揮役が詰まっているときに止められないのが最悪のパターンのため。

tabane report

hooks から呼ばれる内部向けコマンド。人間や指揮役が直接使うことは想定しない。

$ tabane report --pane $TABANE_PANE_ID --state done
  • ペイン ID は PTY 起動時に環境変数 TABANE_PANE_ID として渡す（ptyManager.ts の env 組み立てに追加）
  • Stop hook → done / Notification hook → needs_input / 起動直後 → running

6. 変更対象ファイル

  • src/main/socketServer.ts（新規）— Unix domain socket の listen とコマンド処理
  • src/main/agentState.ts（新規）— エージェント状態の保持と wait の待ち合わせ
  • src/main/ptyManager.ts — env に TABANE_PANE_ID を追加。起動コマンドと権限モードを受け取れるよう create() を拡張
  • src/main/index.ts — socket サーバの起動/終了、renderer へのペイン生成イベント送出
  • src/shared/types.ts — IPC 契約の追加。main → renderer のペイン生成要求、エージェント状態のイベント
  • src/renderer/src/App.tsx — 生成要求を受けて layout 木にペインを追加（handleSplit の経路を再利用）
  • src/main/menu.ts — 「tabane コマンドをパスにインストール」「全ペイン停止」を追加
  • bin/tabane（新規）— socket に繋ぐだけの薄いクライアント
why: ペインを増やす処理自体は App.tsx に既にある（分割ボタンの経路）。今回足すのは「socket から来たときにも同じ処理を呼べるようにする」入口だけで、レイアウト木の操作ロジックには触らない。

7. 残論点 / 合意メモ

決定事項

  • 決定：口は CLI + Unix domain socket（双方向）。MCP は将来拡張として socket の上に被せる
  • 決定：状態は2階建て。ペイン状態（既存の推測）とエージェント状態（hooks の申告）を別軸で持つ
  • 決定：完了通知はブロッキング wait。PTY への割り込み通知は採用しない
  • 決定：権限は --permission で選択、既定は strict。危険側には必ず人間の意思が一度入る
  • 決定：耳は /voice を使い、音声認識は自前実装しない

未決

  • 最重要・実測待ち：/voice が tabane の PTY 内で動作するか。ドキュメントに記載がなく、リモート環境は非対応と明言されている。ローカルの node-pty については未記載のため実機確認が必要。tap モードの方が安定する見込み（hold は Space のキーリピート検出に依存するため xterm.js 越しで化ける可能性）
  • マイク権限：現在の electron-builder.yml に NSMicrophoneUsageDescription の宣言がない。加えて identity: null（無署名）のため、TCC の権限がビルドごとに揮発する懸念がある。上記実測の結果しだいで対応方針を決める
  • 同時ペイン数の上限（具体的な数字）
  • wait --timeout の既定値。claude 側の Bash 実行時間上限との兼ね合いで決める
  • socket のパス。userData 配下に置く想定だが、多重起動時の扱いを決める必要がある
  • yolo（全権限許可）を仕様として持つか、危険すぎるとして落とすか。持つ場合も声で明示したときだけに限定する
  • 上記の /voice 実測が NG だった場合の代替（tabane 側でマイクを取得し writePty で流す）。その場合は音声認識の実装方式が新たな論点になる
